# Разработка mihomo-prizrak-docker

## Назначение и принятые решения

Проект — контейнерная оболочка чистого [Prizrak-Core](https://github.com/legiz-ru/Prizrak-Core), основанная на форке mihomo-mikrotik. Основные сценарии: MikroTik RouterOS и Docker на домашнем Linux-сервере. Поддерживаются `docker run` и Docker Compose.

- По умолчанию собирай последний стабильный релиз Prizrak-Core, без закреплённой в репозитории номерной версии ядра. Новая сборка должна заново определять актуальный релиз, а не бесконечно использовать закэшированный результат определения `latest`.
- В одном запуске CI определяй релиз ядра один раз: тесты и все архитектуры публикуемого образа должны использовать один и тот же разрешённый тег и исходный commit. Версия проекта и версия ядра независимы.
- `PRIZRAK_VERSION=latest` — default самостоятельной сборки; конкретные `PRIZRAK_VERSION`/`PRIZRAK_COMMIT` в CI нужны для согласованной сборки уже определённого релиза. Проверка актуального релиза должна обходить stale cache: одного `RUN curl .../latest` без механизма инвалидирования недостаточно.
- Сохраняй совместимость каталога `/etc/mihomo`, команды-алиаса `mihomo`, `CONFIG`, `WORKDIR`, `SUBn`, `SRVn`, настроек провайдеров и импорта WireGuard/AmneziaWG.
- Стандартный `NETWORK_MODE=proxy` должен работать без `NET_ADMIN`, TUN-устройства и ручного изменения маршрутов, NAT или firewall. `tun`, `tproxy` и `mikrotik` включаются явно. Настройки RouterOS и multi-VETH относятся только к соответствующему режиму.
- Публичные `compose.yaml` и `compose.tun.yaml` запускают готовый `ghcr.io/vrbeeshop/mihomo-prizrak-docker:latest`. Не добавляй в них `build` и настройки локальной сборки. Самостоятельную сборку описывай отдельно через `docker buildx build` с build arguments; `.env.example` содержит настройки запуска, без `PRIZRAK_IMAGE`, `WITH_GVISOR` и `UPX`.
- Отсутствие подписок и узлов даёт рабочую конфигурацию с `DIRECT`; пустые `SUBn`/`SRVn` не создают провайдеры.
- В собственном шаблоне локальные домены и адреса RFC1918/loopback/link-local идут в `DIRECT` до общего маршрута, сопоставления fake-IP сохраняются (`STORE_FAKE_IP=true`). Не относись ко всему `reserved_ips` как к LAN: диапазон fake-IP `198.18.0.0/15` нельзя исключать из его обработки, а CGNAT и личные адреса требуют отдельного решения.
- При стандартном `CONFIG` полный конфиг Mihomo из URL-подписки становится основным: сохраняй его правила, DNS-политики, группы, ноды и провайдеры. Источники проверяются сначала среди `SUBn` по номеру, затем HTTP(S)-`SRVn`; первый полный конфиг выигрывает, остальные конфиги и дополнительные ноды в него не объединяются.
- Из импортированного конфига не применяй настройки портов, API, секрет, панель и сетевой режим устройства-источника. Входящие соединения и TUN формируются контейнером, `DNS_LISTEN` заменяет только адрес DNS-сервиса; правила и DNS-политики подписки не подменяются правилами шаблона. Общие `ipv6`, `log-level` и `find-process-mode` берутся из настроек контейнера.
- Список нод по подписке (URI/Base64, YAML только с `proxies`, Xray JSON) и отдельные URI в `SRVn` используют наш шаблон с его правилами. Явно выбранный пользовательский `CONFIG` имеет приоритет над автоматическим импортом полного конфига; `ENVSUBST=0` также отключает этот импорт.
- Полная подписка обновляется целиком с проверкой и применением через API. `SUBSCRIPTION_INTERVAL` по умолчанию равен `PROVIDER_INTERVAL` (3600 секунд), `0` отключает фоновое обновление; `SUBSCRIPTION_TIMEOUT` по умолчанию 30 секунд. После ошибки загрузки или проверки сохраняй рабочий конфиг. После ошибки API восстанавливай файл и пробуй повторно применить старую версию; не обещай подтверждённый откат работающего ядра, если повторный API-вызов также неуспешен. Для запуска при недоступном сервере используй последнюю валидную копию, связанную с тем же URL; не подставляй кэш другой подписки.
- Служебные данные импорта хранятся в `$WORKDIR/subscriptions/`: `base.yaml`, `active`, кэш `cache/<имя-переменной>.<sha256-URL>.yaml`. Имя кэша атомарно связывает ответ с URL; не разделяй ответ и привязку к URL на независимо обновляемые файлы.
- Загружай подписки с постоянным HWID и настраиваемыми заголовками провайдера, по умолчанию User-Agent `clash.meta`. Не выводи URL с токенами, приватные заголовки и содержимое конфигов в обычные логи. YAML обрабатывай как данные, без `eval` или shell `source` для ответов сервера.
- `--render-config` создаёт конфигурацию без изменения сети, выполнения пользовательских hooks и запуска обновляющего процесса. При URL-подписках он может обращаться к серверу и использовать валидный кэш. Остальные аргументы передаются ядру с сохранением границ аргументов, включая пути с пробелами.

## Настройки по умолчанию

| Назначение | Значение |
| --- | --- |
| HTTP/SOCKS mixed listener | `20170`, TCP и UDP |
| API управления и веб-панель | `9090`, TCP |
| DNS | `1053`, TCP и UDP; в обычном Compose наружу не публикуется |
| Панель | Zashboard; официальный архив последнего релиза скачивается при запуске в каталог `ui` данных контейнера |
| Каталог данных | `/etc/mihomo`, в примерах `./data` |
| Сетевой режим | `proxy` |
| TUN auto-redirect | выключен |
| Сохранение fake-IP | включено (`STORE_FAKE_IP=true`) |

В серверных примерах публикуй прокси и API на loopback. TUN Compose использует host network и явно задаёт необходимые права и устройство; API, mixed listener и DNS остаются на loopback. Переопределение `EXTERNAL_UI_URL` и прочих пользовательских настроек сохраняется. Меняя defaults, согласованно обновляй Dockerfile, Compose, `.env.example`, тесты и примеры README.

Zashboard обслуживается по `/ui/`; корень порта контроллера относится к API. Панель автоматически определяет адрес API по адресу страницы. При `UI_SECRET` первый вход требует пароль; для входа без формы в браузере без сохранённых подключений используй персональную ссылку `/ui/#/setup?secret=<URL-encoded UI_SECRET>`. После входа подключение сохраняется в браузере. В Unraid шаблон ссылки — `http://[IP]:[PORT:9090]/ui/#/setup?secret=...` с фактическим портом контейнера. Не вшивай секрет в публичные HTML/JS панели и не печатай персональные ссылки с секретом в startup logs: UI-статика доступна без API-аутентификации.

## Структура проекта

| Файл или каталог | Ответственность |
| --- | --- |
| `Dockerfile` | Получение чистых исходников актуального Prizrak-Core, кросс-компиляция, варианты gVisor/UPX, runtime-зависимости, defaults и metadata образа |
| `entrypoint.sh` | Bash startup: выбор конфигурации, генерация провайдеров и шаблонов, HWID, пользовательские hooks, явная подготовка сетевых режимов, запуск ядра |
| `runtime/subscription.sh` | Загрузка и выбор полного конфига подписки, кэш последней рабочей версии, периодическая проверка и применение через API |
| `tools/config/` | Небольшой Go-модуль `prizrak-config`: классификация ответа подписки, адаптация YAML к настройкам контейнера и API reload; входит в оболочку, не изменяет исходники Prizrak-Core |
| `mihomo-fs/etc/mihomo_preset/template/default_config.yaml` | Стандартный YAML-шаблон listeners, DNS, групп и правил; значения и блоки подставляются entrypoint |
| `compose.yaml` | Обычный прокси на сервере из готового GHCR-образа, без сборки |
| `compose.tun.yaml` | Самостоятельный Compose-файл для TUN из готового GHCR-образа; не объединяется с обычным Compose |
| `.env.example` | Безопасный образец настроек без настоящих подписок и секретов |
| `VERSION` | Номер версии проекта `MAJOR.MINOR.PATCH`; начальная версия `0.1.0` |
| `.github/workflows/docker-release.yml` | Проверки push/PR, определение версии ядра, сборка и публикация релиза по числовому Git-тегу |
| `scripts/smoke-test.sh` | Проверки настоящего контейнера, API, HTTP/SOCKS, конфигураций и URI-провайдеров без изменения сети хоста |
| `scripts/test-subscriptions.sh` | Интеграционные проверки полного конфига, нод, приоритетов, кэша и live reload с локальным HTTP-сервером внутри изолированного контейнера |
| `scripts/resolve-core.py` | Однократное определение последнего стабильного тега Prizrak-Core и его исходного commit через GitHub API для запуска CI |
| `scripts/release-notes.py` | Проверка фактического `build-info` опубликованного amd64-образа и формирование Markdown-описания GitHub Release |
| `scripts/test-release-tools.py` | Изолированные тесты resolver и генератора описания релиза без сетевых запросов |
| `README.md` | Публичные инструкции использования: Docker run, Compose, MikroTik, настройки и архитектуры |
| `.gitignore`, `.dockerignore` | Исключение секретов, пользовательских данных и временных артефактов |

Стандартный шаблон в данных пользователя обновляется из образа. Изменения маршрутизации пользователя оформляются отдельным готовым YAML либо собственным шаблоном с другим именем; не обещай сохранение ручных изменений сгенерированного default config.

## Git, CI и релизы

- Работай непосредственно в `main`. 
- Сохраняй опубликованную историю upstream. Оформляй изменения понятными тематическими коммитами, не смешивай независимые правки и не переписывай пользовательские коммиты без его запроса.
- Обычные push в любые ветки и pull request запускают только проверки. Они не публикуют образы и не создают GitHub Release; права записи пакетов и релизов доступны только необходимым release jobs.
- Публикацию запускает push числового Git-тега `MAJOR.MINOR.PATCH`, совпадающего с `VERSION`, после успешных тестов. Не ставь тег на старый `HEAD`, пока необходимые изменения не закоммичены. Удаление тега не должно запускать публикацию.
- CI публикует Standard для `linux/amd64`, `linux/arm64`, `linux/arm/v7`, `linux/arm/v5` в `ghcr.io/vrbeeshop/mihomo-prizrak-docker` (для форков namespace выводится из репозитория).
- У опубликованного образа только тег версии проекта и `latest`. Не добавляй SHA-теги, теги вариантов gVisor/UPX или автоматическую публикацию по расписанию. gVisor, UPX и их сочетание остаются опциями самостоятельной сборки; на ARMv5 UPX не применяется.
- После успешной публикации автоматически создавай описание GitHub Release с фактическими версиями компонентов сборки, включая Prizrak-Core и исходный commit. Данные должны соответствовать опубликованному образу, а не быть повторно получены из изменившегося `latest` после сборки.
- Сохраняй build metadata в образе (`/usr/share/prizrak-core/build-info`), чтобы фактический состав можно было проверить. Git commit в metadata допустим; запрет касается тегов образа с хешами.
- Для release notes используй metadata опубликованного образа, полученного по неизменяемому digest. Указывай фактические версии Go и ОС, имена builder/runtime images и применённые build flags с понятной привязкой к архитектуре. Zashboard загружается отдельно при запуске: не приписывай образу фиксированную версию панели, которой в сборке нет.
- Коммит, тег и отправку релиза выполняй в рамках явного запроса пользователя на эти действия. Эти инструкции сами по себе не требуют выпускать релиз после каждой правки.

## Документация

README предназначен для пользователей публичного опубликованного репозитория. Пиши инструкции как для уже доступного GHCR-образа: не добавляй «после первой публикации», «когда образ появится», историю разработки и результаты внутренних проверок без практической пользы читателю.

Сохраняй редакторские решения пользователя, включая изменённые формулировки, удалённые разделы, выбранные порты, панель и примеры. Исправляй связанные несоответствия точечно; не возвращай удалённый текст автоматически. Новые требования и изменения структуры отражай также в этом файле.

## Проверка изменений

- Проверяй Bash-синтаксис каждого изменённого shell-файла отдельным `bash -n` или циклом; `bash -n file1 file2` проверяет только первый файл.
- Для изменений workflow проверяй YAML, выражения GitHub Actions и release conditions (например, `actionlint`), включая ветки, PR, корректный тег, неверную версию, несовпадение с `VERSION` и отсутствие публикации по обычному push.
- Проверяй Compose через `docker compose config` с временным `.env`, не содержащим настоящих секретов.
- Для изменений runtime собирай образ и запускай подходящие smoke-тесты с настоящим ядром: config validation, API, HTTP/SOCKS, загрузка поддерживаемых узлов из URI и сохранение CLI-аргументов. Один `-t` не доказывает, что провайдер действительно загрузил узлы.
- При изменении импорта подписок проверяй оба режима: полный конфиг сохраняет свои правила/DNS/группы, ноды используют шаблон. Проверяй приоритет явного `CONFIG`, выбор источника по номеру, контейнерные порты и сетевой режим, обновление через API, отказ от невалидного обновления и кэш только для того же URL. Для готового образа запускай `bash scripts/test-subscriptions.sh <image>`; unit-тесты Go-модуля — из `tools/config/` командой `go test ./...` через Linux Go либо Linux Go-контейнер.
- Для `latest` и release metadata проверяй, что свежая сборка разрешает актуальную версию и один CI-релиз не смешивает разные версии ядра между архитектурами. Не подменяй фактические версии предположениями.
- При изменении release tooling запускай `python3 scripts/test-release-tools.py`; Python-скрипты используют стандартную библиотеку, без дополнительных pip-зависимостей.
- Проверки не должны менять firewall и маршрутизацию Linux-хоста. TUN/TPROXY на хосте не запускаются как побочный эффект тестов.
- Различай кросс-компиляцию ARM-ядра, запуск ARM-контейнера и проверку на реальном MikroTik. Не заявляй проверку устройства, производительности или туннеля без соответствующего прогона.
- После необходимых успешных проверок не повторяй и не расширяй их без новой причины. Перед коммитами проверь `git diff --check` и состав staged-файлов.
